# 缓存与数据库一致性

## 为什么缓存商户信息

商户详情是典型的"读多写少"数据：读请求远多于写请求，且数据本身不常变化。每次都查 MySQL 会让数据库承担大量重复查询，既慢又浪费连接。于是把商户信息缓存到 Redis，读请求优先命中缓存。

## Cache Aside（旁路缓存）

本项目采用最常用的 Cache Aside 模式，读写的顺序有讲究：

**读流程**

1. 先查 Redis，命中直接返回；
2. 未命中则查数据库；
3. 把结果写回 Redis，再返回。

**写流程**

1. **先更新数据库**；
2. **再删除缓存**（注意是删除，不是更新）。

**为什么是删除而不是更新缓存？**

- 更新缓存容易产生并发写覆盖：两个请求都算出新值，写入顺序不确定，可能留下旧值；
- 缓存很可能是"写多读少"的中间态，算了半天没人读，纯属浪费；
- 删除缓存实现简单，等下一次读请求自然重建。

**为什么先更新数据库再删缓存？** 如果反过来（先删缓存再更新数据库），在"删完缓存、还没提交事务"的窗口里，另一个读请求会把**旧数据**重新加载进缓存，之后就长期是脏数据。先更新库、后删缓存，虽然理论上仍有极小概率出现不一致（读请求恰好在更新前回源），但概率和影响都小得多，配合过期时间基本可控。

## 缓存穿透

**定义**：请求的数据在缓存和数据库中都不存在。缓存永远无法命中，请求每次都打到数据库。若是恶意用户不断伪造不存在的 id，数据库会被打垮。

**三种解法**

1. **参数校验**：在入口挡住明显非法的请求。例如 id 是长整型，传进来的不是数字就直接拒绝。
2. **布隆过滤器**：把已存在的 id 全部哈希进一个位数组；请求先过布隆过滤器，判断"一定不存在"就直接返回。优点是内存极省，缺点是有误判（说存在时可能不存在），且不支持删除。
3. **缓存空值（本项目采用）**：查到数据库为空时，也往 Redis 写一个空值，并设置较短的过期时间（本项目用 `CACHE_NULL_TTL`）。这样后续同样的恶意 id 都会被缓存挡住。空值不能设置太长，否则数据后来真的被创建时，用户会看到"不存在"。

## 缓存雪崩

**定义**：大量缓存 key 在**同一时刻集体失效**，瞬时请求全部涌向数据库。

根因通常是给同一类数据设置了**相同的过期时间**。

**解法**

1. **过期时间加随机扰动**：在固定 TTL 基础上叠加一个随机值，把失效时间打散。
2. **互斥锁**：只放一个线程去查库重建，其余线程等待。
3. **缓存预热**：系统启动或定时任务提前把热点数据加载进缓存，不让请求"冷启动"直接压库。

## 缓存击穿

**定义**：某个**热点 key** 突然失效，大量并发请求同时去查同一条数据，瞬间压垮数据库。注意它与雪崩的区别：击穿是单个热点 key，雪崩是大量 key。

**解法：互斥锁 vs 逻辑过期**

| | 互斥锁 | 逻辑过期 |
| --- | --- | --- |
| 思路 | 只让一个线程回源重建，其余等待 | 缓存永不物理过期，用字段记录逻辑过期时间 |
| 一致性 | 高，等待期间不会有脏数据 | 较低，过期后先返回旧值，存在短暂脏读 |
| 性能 | 差，未抢到锁的线程被阻塞 | 好，主线程立刻返回旧值 |
| 额外开销 | 几乎无 | 需要额外内存存过期时间，需要预热 |
| 实现 | 简单 | 较复杂 |

- **互斥锁**（时间换空间）：用 `SETNX` 抢锁，抢到的线程查库重建，未抢到的休眠重试。重建完成后必须**再次检查缓存**（双检），否则锁释放的瞬间可能又有请求进来重复重建。
- **逻辑过期**（空间换时间）：写入缓存时把数据包成 `{data, expireTime}`，物理上不设 TTL。读到时比较 `expireTime`，未过期直接返回；已过期则获取互斥锁，**开一个独立线程去重建**，主线程立刻返回旧数据。

**为什么逻辑过期要开子线程重建？** 因为它的目标是"不阻塞用户请求"。如果重建还在主线程里同步做，那就退化成了互斥锁。交给后台线程后，主线程快速返回旧值，高并发下吞吐量明显更好，代价是这段时间内读到的是旧数据（可接受，因为热点数据本身变化慢）。

> 注意：逻辑过期**必须先做数据预热**，否则缓存里没有这条数据，第一次访问会因为读不到而误判为"数据不存在"。本项目在 `queryWithLogicalExpire` 里对冷启动做了兜底：缓存缺失时回源数据库并建立逻辑过期缓存。

## 强一致需求：Redisson 读写锁

Cache Aside 是最终一致，存在不一致窗口。如果业务要求"写的同时不允许读到旧值"，可以用读写锁：

- 读操作加**共享锁**：读读不互斥，并发读不受影响；
- 写操作加**排他锁**：读写、写写、写读全部互斥；
- 读写使用**同一把锁**，才能互斥。

这样在写数据期间，其他线程读不到。代价是吞吐下降、复杂度上升，只适合对一致性要求极高的少数场景。本项目在 `CacheClient` 中区分了普通缓存与逻辑过期缓存两条路径，按业务重要性选用。
