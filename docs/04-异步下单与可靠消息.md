# 异步下单与可靠消息投递

## 同步秒杀的瓶颈

最初的秒杀流程是串行走数据库的：

```
查优惠券 -> 查订单（一人一单）-> 扣库存 -> 创建订单
```

四步全是数据库操作，还叠加了分布式锁。用 JMeter 压测的结果是：**吞吐量低、平均耗时高、异常率高**。原因是每一步都要等上一步完成，而 MySQL 的并发能力远不如 Redis。

关键观察：**下单成功的判定条件其实很轻**——只要"库存充足"且"该用户没买过"，这一单就一定能成。剩下的落库、扣减只是"迟早要完成"的动作，不需要用户等。

## 优化思路：判断前置到 Redis，落库异步化

把流程拆成两段：

1. **资格预检（同步、极快）**：在 Redis 里判断库存、判重，通过就直接告诉用户"下单成功"，返回订单号；
2. **订单落库（异步、慢就慢）**：把订单信息丢进消息队列，后台消费者慢慢写数据库。

用户几乎无感知等待，系统吞吐量大幅提升。

## 为什么用 Lua 做预检

预检包含多个步骤：读库存 → 判断 → 判断用户是否下过单 → 扣减库存 → 记录下单用户 → 投递消息。如果分成多条 Redis 命令执行，中间任何一步都可能被其他线程插入，产生竞态。

Redis 单条命令是原子的，但多条命令不是。把这一串逻辑写进 Lua 脚本后，Redis 会把整个脚本当作一个整体执行，**无需额外加锁就实现了天然互斥**，同时把多次网络往返压缩成一次。

`seckill.lua` 的返回值约定：

| 返回值 | 含义 |
| --- | --- |
| `0` | 校验通过，已扣减库存并写入待投递消息 |
| `1` | 库存不足 |
| `2` | 重复下单 |
| `-1` | 缓存中找不到库存（未预热） |

脚本的最后一步不是直接发消息，而是把订单写入 **Redis Stream**——这是下一节的可靠性设计。

## 可靠性核心：Redis Stream 作为 Outbox

先看一个容易被忽略的问题：**如果 Lua 扣完库存、但消息没发出去就宕机了，会发生什么？**

库存已经扣了，用户却被通知失败，而订单永远不会落库——库存凭空少了一件，且没有任何记录可以追溯。这类"业务已完成、消息丢失"的问题，靠简单的"发消息 + 重试"是解决不了的。

本项目的做法是把 Redis Stream 当作 **Outbox（发件箱）**，让"扣库存"和"待投递消息"在同一个 Lua 脚本里原子完成：

- Lua 中 `XADD stream.orders` 写入待投递订单，与扣库存是同一个原子操作；
- 一个定时任务 `RedisStreamOrderRelay` 每 500ms 读取 Stream，把消息**转发到 RabbitMQ**；
- **只有 RabbitMQ 返回 broker confirm（发布确认）后，才 `XACK` 这条 Stream 消息**；
- 转发失败或进程重启时，消息留在 Stream 的 PEL（Pending Entries List）中，下一轮继续投递。

这样一来，"至少投递一次"由 Stream 保证，"队列内部可靠路由"交给 RabbitMQ。RabbitMQ 侧开启了 `publisher-confirm-type: correlated` 与 `mandatory`，确保消息确实到达交换机。

## RabbitMQ 三级补偿链路

消息进入 RabbitMQ 后，用一条正常链路 + 两级兜底来处理消费失败：

| 阶段 | 队列 | 触发条件 | 处理方式 |
| --- | --- | --- | --- |
| 正常消费 | `seckill.order.queue.v2` | — | 落库 + 扣减数据库库存，成功即 ACK |
| 重试补偿 | `seckill.order.retry.queue.v2` | 正常队列消费失败（NACK 不重回原队列） | 再试一次，成功即 ACK |
| 失败兜底 | `seckill.order.failure.queue.v2` | 重试队列再次失败 | **无消费者**，保留消息供人工排查与重放 |

> ⚠️ **面试注意**：这里的重试队列**没有配置 `x-message-ttl`**，所以它是**立即重试**，不是延迟队列。
> 如果被问到"延迟队列怎么实现"，要如实说明，别说成延迟重试。想真正实现延迟重试，可以给队列加
> `x-message-ttl`，或使用 `rabbitmq-delayed-message-exchange` 插件。

设计要点：

- 失败消息**绝不静默丢弃**，最终一定落在失败队列里，可以人工介入；
- 消费失败用 `basicNack(requeue=false)` 而不是 `requeue=true`。后者会把"毒消息"（永远处理失败的坏消息）无限重投，把消费者卡死；
- 采用**手动 ACK** 模式，只有订单与库存事务真正提交后才确认，避免"ACK 了但事务回滚"导致丢单。

## 幂等：重复消费怎么办

Stream 保证至少投递一次，RabbitMQ 失败重试也会重复投递，所以消费者必须能处理**同一条消息被消费多次**：

- 落库前先按订单 ID 查询，已存在则直接跳过；
- 同一用户 + 同一优惠券也做一次判重；
- 数据库对订单 ID 建立唯一索引作为最后防线，若并发下仍撞上，捕获 `DuplicateKeyException` 并当作"已处理成功"正常 ACK。

三重防护合起来，保证重复消息不会产生重复订单。

## 一次下单的完整链路

```
前端请求秒杀
  │
  ├─ 校验秒杀时间窗
  ├─ 生成全局唯一订单号（Redis 自增 ID 方案）
  │
  ├─ 执行 seckill.lua（原子）
  │     ├─ 库存不足      -> 返回 1
  │     ├─ 重复下单      -> 返回 2
  │     └─ 通过 -> 扣 Redis 库存 + 记录下单用户 + XADD 到 Stream
  │
  └─ 立即返回订单号给前端

RedisStreamOrderRelay（定时 500ms）
  │
  ├─ 读取 Stream（先扫 PEL 重试，再读新消息）
  ├─ 投递 RabbitMQ，等待 broker confirm
  └─ confirm 成功才 XACK；失败则保留，下轮重试

SeckillVoucherListener（手动 ACK）
  │
  ├─ 幂等校验
  ├─ 事务内：扣数据库库存（stock > 0）+ 订单落库
  ├─ 成功 -> basicAck
  └─ 失败 -> basicNack(requeue=false) -> 重试队列 -> 失败队列
```

## 故障注入验证

`bench/` 下有三个 Python 脚本，用故障注入的方式验证上面这套设计确实成立。脚本依赖均为标准库，结果会输出为 JSON 便于比对：

| 脚本 | 验证内容 |
| --- | --- |
| `bench/seckill_correctness.py` | 并发下单的正确性：库存 100、1000 个用户、200 并发，断言成功订单数恰为 100，无超卖、无重复 |
| `bench/rabbitmq_fault_injection.py` | 停掉 RabbitMQ 后下单：断言消息停留在 Redis Stream 的 PEL 中；RabbitMQ 恢复后订单最终落库 |
| `bench/mysql_fault_injection.py` | 停掉 MySQL 后下单：断言订单消息被保留在持久化的失败队列中，不会丢失 |
| `bench/cache_hot_benchmark.py` | 热点商品接口的吞吐与延迟基准 |

实测参考（`bench/results/`）：

- 库存 100 / 1000 请求 / 200 并发：QPS ≈ 561，p99 ≈ 393ms，成功订单数 = 100（正确）；
- RabbitMQ 中断：`pending_during_outage = 1`，恢复后 `persisted_after_recovery = true`。
