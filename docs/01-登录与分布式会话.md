# 登录认证与分布式会话

## 要解决的问题

单体应用把登录状态放在 `HttpSession` 里就够了，但一旦部署成多台 Tomcat 的集群，就会出现会话不共享的问题：

- 用户在 A 节点登录，Session 落在 A 节点内存里；
- 后续请求被负载均衡转发到 B 节点，B 节点找不到这份 Session，用户就"莫名其妙掉线"。

根因是 Session 存在**单个 JVM 的堆内存**中，天然无法跨节点共享。

## 方案一：Redis 保存登录态（本项目采用）

把用户信息从 Session 搬到 Redis，用随机 Token 作为 key：

1. 用户提交手机号 + 验证码；
2. 校验通过后生成一个随机 Token（UUID），把 `UserDTO` 序列化后写入 Redis，并设置过期时间；
3. Token 通过响应头返回，前端保存后每次请求带上；
4. 后续请求从请求头取出 Token，用 Token 去 Redis 查用户，命中则续期。

这样做的好处：

- **天然的分布式共享**：所有节点读同一份 Redis，不存在节点差异；
- **可控的过期策略**：续期逻辑完全由自己掌控，还能顺手实现"活跃即续期"；
- **可主动失效**：退出登录直接删 key，不像 Session 需要广播失效。

## 方案二：JWT / 客户端 Token（对比）

另一种思路是服务端完全不存状态，把用户信息签名后交给客户端保存。它省掉了服务端存储和一次 Redis 查询，但代价是：

- Token 一旦签发就无法主动作废，除非额外维护黑名单（又绕回了服务端存储）；
- 续期不方便，通常只能靠短有效期 + refresh token 组合。

因此本项目选择方案一：**登录态需要"可撤销"和"可续期"，Redis 更合适**。

## 双层拦截器的职责划分

代码里有两个拦截器（见 `config/MvcConfig.java`），执行顺序靠 `order` 控制：

| 顺序 | 拦截器 | 拦截范围 | 职责 |
| --- | --- | --- | --- |
| 0 | `RefreshTokenInterceptor` | `/**`（全部请求） | 解析 Token、查 Redis 用户、写入 `UserHolder`、刷新有效期 |
| 1 | `LoginInterceptor` | 排除登录、店铺浏览等公开接口 | 校验 `UserHolder` 中是否有用户，没有则拦截返回 401 |

拆成两层的原因：

- **续期要覆盖所有请求**。如果把续期写在只拦截部分路径的登录拦截器里，那些公开接口（比如浏览店铺）就不会触发续期，用户会"越用越容易过期"。
- **鉴权只针对需要登录的路径**。公开接口没必要做登录判断，放在第一层会带来无谓开销。
- **职责单一**。第一层只做"识别用户 + 续期"，第二层只做"要不要拦"，互不干扰，扩展时也只需改其中一层。

## 用 ThreadLocal 传递用户

拦截器解析出的用户要能被 Controller、Service 直接拿到，但又不想层层传参，于是用 `UserHolder` 包装 `ThreadLocal`：

- `RefreshTokenInterceptor.preHandle` 中 `UserHolder.save(user)`；
- 业务代码任意位置 `UserHolder.getUser()` 即可取到；
- 关键：`afterCompletion` 中必须 `UserHolder.remove()`。

**为什么一定要 remove？** Tomcat 的工作线程是复用的，若不清理，下一个请求复用同一线程时会读到上一个用户的身份，造成**越权**，而且这种 bug 在低并发测试时几乎不会暴露。
