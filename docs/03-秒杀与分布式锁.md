# 秒杀：超卖、一人一单与分布式锁

## 超卖是怎么发生的

秒杀扣库存的原始写法是"先查后改"：

```java
// 1. 查库存
SeckillVoucher v = getById(voucherId);
// 2. 判断
if (v.getStock() > 0) {
    // 3. 扣减
    updateStock(voucherId, v.getStock() - 1);
}
```

问题出在第 2 步和第 3 步之间：线程 A 查到库存为 1，还没来得及扣减，线程 B 也查到库存为 1，于是两个线程都把库存扣到 0，实际卖出了 2 件——**超卖**。

## 悲观锁 vs 乐观锁

| | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 假设 | 认为一定会冲突，操作前先加锁 | 认为一般不会冲突，提交时再校验 |
| 做法 | `synchronized`、数据库行锁、分布式锁 | 版本号 / CAS |
| 代价 | 串行化，性能一般，实现简单 | 失败需重试，但并发吞吐更好 |
| 适用 | 写多、竞争激烈 | 读多、竞争较少 |

本项目采用**乐观锁**。具体做法是在 SQL 的 `where` 里直接附加库存判断，把"判断"和"扣减"合并成一条原子 SQL：

```sql
update seckill_voucher
set stock = stock - 1
where voucher_id = ? and stock > 0
```

这样数据库的行锁保证了这条语句的原子性，`stock > 0` 不满足时更新影响行数为 0，说明抢购失败。

> 常见误区：乐观锁不一定要用版本号。版本号适合"通用更新"，而在库存这种"只要还有就能扣"的场景下，直接把业务约束写进 `where` 条件更简单高效，也避免了版本号冲突导致的大量失败。

## 一人一单：为什么 JVM 锁不够

秒杀通常限制每个用户只能买一单。直觉写法是加 `synchronized`：

```java
synchronized (userId.toString().intern()) {
    // 查订单 -> 不存在则创建
}
```

单机下没问题，但集群下彻底失效：`synchronized` 只能锁住**当前 JVM 内**的线程，而多台服务器的 JVM 之间互不可见。用户的两笔请求被分发到不同节点，就会各创建一单。

要跨进程互斥，锁必须放在所有节点都能访问的外部存储上——也就是 **Redis 分布式锁**。

## 自己实现一把 Redis 分布式锁

思路很简单：用 `SETNX` 抢占一个 key。

```java
// 加锁：key 不存在才能设置成功
SET lock:order:{userId} {threadId} NX EX 10
```

但有两个坑必须处理：

**坑一：锁被别的线程误删。**
线程 A 拿到锁后执行业务超时，锁自动过期，线程 B 拿到锁；此时 A 执行完成把锁删了，删掉的是 B 的锁。解决办法是把 `threadId` 作为 value 存进去，**删锁前先比对是否是自己的**。

**坑二：比对和删除不是一个原子操作。**
"GET 出来比一比，再 DELETE"中间仍可能被插入其他操作。解决办法是把这段逻辑写进 **Lua 脚本**，让 Redis 原子执行（见 `unlock.lua`）。这是"多条命令需要原子性时用 Lua"的典型场景。

对应实现：`utils/SimpleRedisLock.java`（加锁 `setIfAbsent` + Lua 释放）、`utils/ILock.java`。

## 生产级方案：Redisson

手写锁还要处理可重入、续期、重试等一堆细节，生产上直接用 Redisson。它解决的几件事：

**1. 可重入**
同一线程多次获取同一把锁不会死锁。底层用 Hash 结构：大 key 是业务锁名，小 key 是线程唯一标识，value 是重入次数。重入时 `+1`，释放时 `-1`，减到 0 才真正删 key。

**2. 可重试 + 看门狗续期**
获取锁时可以指定等待时间和超时时间。若业务执行时间超过锁的过期时间，**看门狗（Watch Dog）**会定期检查线程是否还持有锁，持有就自动续期，避免业务没跑完锁就过期了。此外，抢锁失败的线程不是立即报错，而是自旋等待一段时间，锁一释放就能立刻拿到，高并发下性能更好。

**3. 主从一致性：联锁（MultiLock）**
Redis 主从是异步复制的：线程在主节点加锁成功，主节点还没来得及把锁同步给从节点就宕机了，从节点升为主节点后，这个锁就"消失"了，其他线程能重复加锁。

联锁的思路是不再依赖主从，而是**向多个独立节点同时加锁，全部成功才算成功**。可用性随节点数增加而提高；某个节点宕机，只要其余节点仍持有锁，锁就依然有效。
